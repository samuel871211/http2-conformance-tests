# 待實作的黑箱測試案例

## 說明

- 共 100 個案例：批次 A 有 50 個，批次 B 有 50 個。
- 編號格式：`A-01` 到 `A-50`，`B-01` 到 `B-50`。
- 兩個批次互不重複，也不與 `src/tests` 現有測試重複。
- 「預期行為」欄位的簡寫：
  - `GOAWAY(X)`：connection error，error code 為 X。
  - `RST(n, X)`：stream n 的 stream error，error code 為 X。
  - 「正向」：server 應正常處理，不應回報 error。
- RFC 只寫 SHOULD 或 MAY 的案例，assert 時建議接受多種合規結果。

### 批次 A 構造重點

- **A-05**：先開 stream 1（不帶 END_STREAM），再連送 4 個 16,384 bytes 的 DATA，最後補 1 個 1 byte 的 DATA，總共 65,536 bytes。這比預設 initial window（65,535）多 1 byte。
- **A-21**：先開 stream 1（不帶 END_STREAM），送 WINDOW_UPDATE（stream 1，`2^31-1 - 65535`），讓 server 端的 stream send window 剛好等於 2^31-1。接著送 `SETTINGS_INITIAL_WINDOW_SIZE = 65536`，window 會超過上限 1。
- **A-22**：要讓 server 實際回 response，所以需要設定 `on("stream")` handler。
- **A-26**：直接送 WINDOW_UPDATE（stream 0，`2^31-1`）。加上初始的 65,535 就超過上限。
- **A-45**：現有的 `headers-with-indexed-header-field-index-62.ts` 測的是 Indexed Header Field。這個案例改成 Literal Header Field 的 name reference（prefix `01` + index 62），是另一條 decode 路徑。
- **A-50**：stream 1 的 HEADERS 用 incremental indexing 送 `x-test: 1`，再加一個大寫的 `TEST: 123` 讓它變成 malformed，預期收到 RST。stream 3 送一個正常 request，其中用 index 62 引用 `x-test`。驗證 server 有沒有因為丟棄 malformed request 而漏掉 HPACK 狀態更新。

### 批次 A 的注意事項

- A-05、A-39、A-44 的 RFC 用詞是 SHOULD，或沒有規定唯一的處理方式。assert 時建議接受多種結果（例如 RST 或 400 都算通過）。

### 批次 B 構造重點

- **B-04**：送 4 個 DATA，每個 payload 都是 16,384 bytes，帶 PADDED、pad length 255。這樣 flow control 計入 65,536 bytes（超過 window 1 byte），但實際資料只有 64,512 bytes。只計算資料部分的實作不會報錯，會被抓出來。
- **B-05**：先開 stream 3（不帶 END_STREAM），再對從未開啟過的 stream 1 送 DATA。
- **B-06**：stream 1 送 HEADERS（不帶 END_STREAM），接著送 RST_STREAM（CANCEL），再對 stream 1 送一次 HEADERS。
- **B-08**：Node.js server 要設定 `settings: { maxConcurrentStreams: 1 }`。外部 server 則要從它的 SETTINGS 讀出上限。
- **B-16 / B-17**：用 `http2ConnectionPreface(socket, settingsFrame)` 帶 `SETTINGS_INITIAL_WINDOW_SIZE=0`。B-17 接著再送 `SETTINGS_INITIAL_WINDOW_SIZE=100`。
- **B-22**：在 stream 0 送 increment `0x80000001`。若實作沒有忽略 reserved bit，會讀成 2^31+1，超過上限而回 FLOW_CONTROL_ERROR。
- **B-38**：`content-length: 18446744073709551617`（2^64+1），再送 1 byte 帶 END_STREAM 的 DATA。
- **B-42**：name `x`（1 byte）+ value 4,063 bytes + 32 = 4,096。
- **B-43**：value 用 Huffman code 很短的字元（例如 `0`，5 bits）重複 4,064 次。編碼後大約 2.5 KB，但解碼後 entry size 是 4,097，應該清空整個 table。
- **B-45**：依序加入 A、B、C 三個 entry，每個 size 約 1,400。加入 C 時 A 會被驅逐，table 變成 [C, B]，index 64 不存在。

### 批次 B 的注意事項

- B-16、B-17、B-18、B-25、B-36、B-41、B-44、B-50 需要 server 有 handler 回 body，或把收到的 header 回傳。用 Node.js server 時可以在 `on("stream")` 裡處理。外部 server 需要提供對應的 endpoint。
- B-08、B-11、B-12、B-31、B-32、B-33、B-37 的 RFC 用詞是 SHOULD、MAY，或有多種合規處理方式。assert 時建議接受多種結果。
